# 文档复审管理

产品文档在每次发布后都需要有人对真实性负责。本机制把「负责人、校验范围、完成日期」公开在页脚，
把「维护任务、责任交接、审阅证据」保存在后台与 PostgreSQL 中，并保证转派、到期、内容变化等场景
都不破坏历史事实。

## 页脚公开什么

每个文档页底部展示一条复审信息条：

- **负责人**：当前责任人（离职/小组调整后显示继任者）。
- **校验范围**：本次签收**实际**校验通过的覆盖节点，如 `examples/button/basic.vue`、`api/button`。
- **声明范围**：页面承诺应覆盖的范围（glob）。签收时审阅项覆盖图必须满足声明范围，否则不允许签收。
- **完成日期与签收人**：取最近一次签收的真实时间，可在 `Asia/Shanghai` 与 `UTC` 间切换；底层时刻不变。
- **状态徽标**：`信息已核实` 或黄色的 `信息需核实`。黄色徽标下方直接列出**原因**，而不只是一个标签。

部分完成时（partial），页脚只列出真正通过的范围，并明确写出哪些节点未覆盖及原因——
**公开日期反映真实完成范围，不允许用局部检查冒充整篇复审。**

## 后台任务如何产生

维护任务有三种来源：

| 来源 | 触发方式 | 幂等键 |
| :-- | :-- | :-- |
| 发布版 | 每次发布版发布时，为版内每个页面生成一条任务 | `release:<version>` |
| 固定周期扫描 | 扫描器按页面时区把时间划入周期桶，每桶最多一条 | `cycle:<period>d:<bucketStart>` |
| 依赖变更 | 依赖图计算受影响页面，依赖发版即触发 | `dep:<depId>:<depVersion>` |

- 同一幂等键重复触发不会产生第二条任务，扫描器和依赖 webhook 都可以安全重跑。
- **两类（实际是三类）任务会合并**：同一页面若已有打开任务，新触发并入其中，
  只保留一条待办，审阅项与触发来源累加；已有校验进展的任务优先作为幸存者，证据不丢失。
- 任务到期后提醒分 `due_soon` 与 `overdue` 两类，每类每任务只发一次，提醒任务重跑幂等。

### 固定周期扫描 vs 依赖变更触发

- **固定周期扫描**解决「没人动它，但时间久了可能过时」：按页面配置的周期（默认 90 天）与
  **站点时区**计算周期桶，跨时区部署时桶边界按各自本地日历对齐。
- **依赖变更触发**解决「上游变了，文档必须跟着核实」：只通知依赖图上实际受影响的页面与审阅项，
  并把相关项升一个版本。
- 二者互补：依赖触发命中正在等待周期复审的页面时直接合并，维护者不会收到两张重复待办。

## 责任交接与证据

- 负责人**离职**或**小组调整**时，操作是「转派待办」：其名下打开的任务改派给继任者并记录流水
  （谁→谁、原因、时间）。**历史签收记录中的签收人永不改写**——曾签收者是历史事实。
- 没有继任者时，任务进入 `blocked_no_owner`：不能签收、不会消失，指定继任后自动恢复。
- PostgreSQL 中 `review_signoff`、`review_check`、`review_evidence`、`owner_handover`
  均为 append-only，并由触发器禁止 `UPDATE/DELETE`。签收时固化范围快照、正文哈希与证据（截图/日志/链接）。

## 复审到期与正文变化

两条核心原则：

1. **到期只提示，不撤内容。** 超过周期未重新全量签收，页面状态变为 `needs_verification`，
   页脚提示「信息需核实」，但历史内容与历史签收始终可读、可查。
2. **正文关键变化使相关项待重验。** 正文或依赖变化命中审阅项时，该项生成新版本，
   旧版本上的检查结论不再代表当前内容；必须重验后才能签收。签收时若发现页面哈希已变化，
   直接拒绝签收（防止「校验的是旧版、签收的是新版」）。

## 维护者看到「为何超期」

维护后台对每个超期页面给出原因链，而不仅是黄色标签，例如：

- 无继任负责人：责任人离职后未指定继任，待办被阻塞；
- 正文或依赖关键变化，相关审阅项已升版本，旧结论失效需重验；
- 存在检查失败项未整改（列出具体节点与备注）；
- 任务自某时刻起超期（附触发来源）与转派流水；
- 固定复审周期已到，最近全量签收仅代表当时内容。
